## 2. 변경 내용과 **회귀가 아닌 근거**

1. `python-jose[cryptography]==3.4.0` → **`3.5.0`** (`requirements.txt`·`requirements.oracle.txt` **둘 다**).
   - 회귀 아님: 3.5.0 > 3.4.0 이라 기존 하한(인증 우회 방지)을 **그대로 만족**한다.
   - 두 매니페스트를 함께 올린다 — 한쪽만 올리면 *"CI 는 초록인데 프로덕션은 취약"* 이 된다(#721 전례).
2. `_MIN` **(3,4,0) → (3,5,0)** 으로 상향 + 실패 문구에 **두 이유를 모두** 적는다.
3. 독스트링의 *"제약상 올릴 수 없다"* 를 **재측정 결과로 교체**한다(거짓이 된 근거를 남기지 않는다).
4. **하지 않기로 한 것을 잠근다** — `pyasn1` 직접 핀 금지 가드 신설.

## 3. ★검증하지 못한 것

1. **실제 CI 의 pip-audit 결과는 아직 못 봤다.** 로컬 해석으로 pyasn1 0.6.4 를 확인했을 뿐이다.
   `pip-audit` 은 자체 해석기를 쓰므로 **CI 실행이 진짜 판정**이다. ★이 PR 의 CI 를 봐야 종결이다.
2. **pyasn1 외 나머지 CVE 는 그대로다** — 베이스라인 안의 pyjwt 7건·python-jose 3건·
   python-multipart 7건 등은 이 PR 이 건드리지 않는다. 이 PR 은 **베이스라인 초과분 4건**만 없앤다.
3. **런타임 회귀는 단위 테스트로만 봤다.** 실제 로그인/WS 인증 라이브 확증은 배포 후에만 가능하다.
   `jose 3.5.0` 은 로컬에 설치돼 있어 심볼 실호출까지 했으나, **컨테이너에서 도는 것과 같다는 보장은 없다**.
4. **3.5.0 의 변경 로그를 읽지 않았다.** API 호환은 우리 소비처가 쓰는 심볼로만 확인했다.
5. `Security Scan` 은 **필수 체크가 아니다**(main 보호 필수 4종에 없음). 따라서 이 PR 이 머지돼도
   **다른 PR 을 막고 있던 것은 아니다** — 인계서의 *"상시 빨간 게이트는 곧 꺼진다"* 가 진짜 위험이다.

### ★리뷰가 찾은 **환경 오염** — 내 거짓 SURVIVED 의 원인

내가 «④ `_MIN` 변이 SURVIVED» 를 보고했다가 재현되지 않아 **원인 미상**으로 남겼는데,
리뷰가 특정했다: pytest 어서션 재작성 캐시의 **좀비 `.pyc`**. `(3,4,0)` 과 `(3,5,0)` 은
**바이트 길이가 같고** mtime 도 **같은 초**라, pytest 의 `(mtime, size)` 검증을 통과해
**낡은 바이트코드가 영구히 서빙**됐다.

★**교훈**: 이 파일을 만지는 세션은 변이 전에 `rm -rf tests/__pycache__` 를 선행하라.
그리고 **원인 미상으로 남긴 도구 이상은 도구가 아니라 환경일 수 있다.**

### 리뷰가 **반증에 실패한 것**(= 살아 있음)

핵심 처방은 4개 축에서 **독립 확증**됐다 — ①CI 와 동일 핀(`pip-audit 2.10.1`)으로 실제 게이트
스크립트 실행 → **`새 취약점 없음` · GATE_RC=0** ②두 매니페스트 각각 별도 해석 → 둘 다 `pyasn1 0.6.4`
③3.5.0 에서 **새 취약 ID 0**(`ecdsa PYSEC-2026-1325` 는 베이스라인 기등재) ④런타임 회귀 —

## 3. 배포 절차

```bash
scripts/coord.sh claim '<내용 · 지표 · ★예측>'      # 예측을 적어 두어야 나중에 판정이 된다
# 선갱신(★필수 — 안 하면 스크립트 변경이 한 판 지연된다)
ssh -i ~/.oci.key ubuntu@<서버> 'cd ~/Development_AI && git fetch origin main -q && git reset --hard FETCH_HEAD -q'
# 168 먼저 → 158 (백엔드가 계약을 담아야 화면이 표시한다)
ssh -i ~/.oci.key ubuntu@168.110.125.89 'setsid bash ~/deploy.sh </dev/null >/tmp/deploy168.log 2>&1 &'
ssh -i ~/.oci.key ubuntu@158.179.174.207 'cd ~/Development_AI && nohup propai-platform/scripts/safe-deploy.sh web main >/dev/null 2>&1 &'
scripts/coord.sh release '<지표 전후 · 대조군 · 무회귀>'
```

- **SSH 는 반드시 `-i ~/.oci.key`** — `.ssh/` 키는 거부된다(그것을 "키 미등록"으로 오독한 세션이 둘 있었다).
- **168 에 `safe-deploy.sh` 를 쓰지 마라** — 트래픽 없는 compose 스택만 갱신하고 "성공"을 찍는다.
- **sw 캐시명을 손으로 올리지 마라** — 빌드가 자동 채번한다(3중 fail-closed). 범프 PR 은 §E-22 순서 결함을 되살린다.
- **배포 판정 = 커밋 수가 아니라 런타임 델타**(주석·테스트 제외한 실효줄).
- **멈춤 판별은 상태문자열이 아니라** 로그 갱신 + `docker stats` CPU + **프로세스 트리**로.
  프론트 빌드는 15~26분이 정상이고 `pnpm build` 구간은 출력 없이 조용하다.

## 4. ★검증 규율 — 전부 이전 세션이 실제로 밟은 함정이다

- **`0`/`null` 은 부재가 아니다.** 조회기 사망일 수 있다. **양성 대조군**(반드시 잡혀야 하는 것)을
  먼저 통과시켜라. 실제 사고: `walk(d)` 호출 누락 · `md5sum|cut` 빈 값(파이프 종료코드 0) · payload 키 오독.
- **지표는 문자열 리터럴**로 골라라. 식별자(컴포넌트·함수명)는 최소화로 사라진다.
  **주석 속 문구도 번들에서 제거**되므로 소스에서 **렌더 문자열인지 주석인지 갈라라**.
- **이미 존재하는 문자열은 판별력 0** — 배포 전 값이 0 인지 먼저 재라.
- **`cmd | head` 는 파이프 끝의 종료코드**를 준다. `$?` 로 판정하지 마라.
- **`gh pr edit --base` 는 조용히 실패**한다 → `gh api -X PATCH repos/:owner/:repo/pulls/N -f base=main --jq .base.ref`.
- **외부 변경 명령은 결과물로 재확인**하라(종료코드 0 이어도).
- **커밋 먼저 → 변이 → 원복.** 미커밋 `git checkout --` 는 편집을 날린다. `scripts/mutate_manual.sh` 를 써라(#726 착지 시).
- **부분 출력에서 전체 부재를 추론하지 마라.**
- **이름이 같아도 같은 것이 아니다** — `development_plans.special_districts` ≠ 최상위 `special_districts`.
- **피어 세션 보고를 액면 수용하지 마라.** 이전 세션은 재측정으로 여러 번 이득을 봤고,
  동시에 **피어가 내 오류를 잡아 준 적도 여러 번** 있다. 서로 재는 것이 이 팀의 방식이다.

## 5. ★진행 중이던 판단 (재보고 정하라)

**158 prune 창 크기.** `docker image prune -f --filter "until=24h"` 를 손으로 돌려
디스크 **50% → 18%**(12GB) 회수했다. 그러나 **다음 빌드의 캐시 히트가 0** 이 되어 빌드가
**26분**(평소 15~20분)이 됐다.

> **"until=24h 는 캐시를 지킨다"는 서술은 168 에서만 참이고 158 에서는 거짓이다.**
> 158 은 배포 간격이 길어 하위 레이어(베이스·`pnpm install`)가 24시간을 넘긴다.

→ **다음 158 배포의 캐시 히트를 보고 `until=72h` 이상으로 정한 뒤** 스크립트 PR 을 내라.
**재보지 않은 상수를 코드에 박지 마라.** (168 은 `until=24h` 로 39초를 유지하므로 건드리지 마라.)

## 6. 구조적 문제 (사용자 결정 필요 — 통합자가 결정하지 마라)

**머지 큐.** CI 약 14분 vs main 커밋 간격 약 14분이라 **초록 PR 이 구조적으로 정체**된다.
브랜치 보호가 `strict=true` 라 최신화가 필수인데, CI 가 끝나는 순간 다른 머지가 들어와 다시 BEHIND 가 된다.
한 PR 이 자동 리베이스를 **6회** 하고서야 붙은 사례가 있다.
→ 재시도를 반복하지 말고 **auto-merge 를 걸어 둔 채 경합에서 이길 때 들어가게** 두고,
급한 PR 은 보드로 요청받아 **그 건에 양보**하는 식으로 운영하라.

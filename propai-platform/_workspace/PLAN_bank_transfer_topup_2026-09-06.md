# 무통장입금 충전 — 계획서 (2026-09-06)

> **요구**: *"우선 무통장입금으로 새마을금고 9002148908909 예금주:강재희로 처리되도록 하고,
> 관리자가 입금확인으로 승인하면 충전되도록"*

---

## 0. 옵시디언 조회 결과 (계획 게이트 §0)

★**조회 실패**. `/mnt/d/...` 접근이 `No such device`.

★★**진단 정정(2026-09-06 15:0x)** — 처음에 *"드라이브 미마운트(장치 부재)"* 라고 적었는데
**틀렸다.** `mount` 를 보면 **마운트는 살아 있다**:

    D: on /mnt/d type 9p (rw,relatime,aname=drvfs;path=D:;...,rfd=3,wfd=3)

즉 **9p 전송이 끊긴 것**이다(대조군: `/mnt/c` 는 `ls -d /mnt/c/Windows` 정상).
**처방이 다르다** — 「드라이브를 마운트한다」가 아니라 **WSL 재시작**(`wsl --shutdown`)이다.
★`ls` 하나만 보고 원인을 단정했다가 다음 사람을 틀린 처방으로 보낼 뻔했다
(§증거 규율 2: 인과 주장에는 증거 토큰이 필요하다 — `mount` 출력이 그 토큰이다).

따라서 볼트의 기각 이력·전례는 **미측정**이며, 「없다」고 말하지 않는다.
사유 구분: **접근 실패**(권한 부족도, 사건 미발생도, 장치 부재도 아니다).

대신 **저장소 안에서** 같은 네 항목을 실측했다(§1 전제표가 그 결과다).

## 1. 전제 표 — ★**「없다」고 결론 내리기 전에 형제를 훑었다**(§29)

첫 인상은 *"무통장입금을 새로 만들어야 한다"* 였다. **틀렸다.** 실측 결과 **절반이 이미 있다.**

### 1-A. 이미 있는 것 — **재구현하지 않는다**

| # | 이미 있는 것 | 확인 방법 | 원문 |
|---|---|---|---|
| E1 | **관리자 수동 확정 API** | `grep '^@router\.' routers/billing.py` 파생 전수 | `POST /admin/orders/{order_id}/confirm` — 독스트링이 문자 그대로 *"관리자 수동 지급 확정(**계좌이체 확인** 대응) — 총괄관리자(tier=super_admin) 전용"* |
| E2 | **그 API 의 관리자 UI** | `git grep 'admin/orders' -- apps/web` | `PaymentAdminPanel.tsx:185` `manualConfirm()` — 주석: *"계좌이체 등 오프라인 입금 확인 후 관리자가 직접 지급한다(`provider="manual"`)"* |
| E3 | **원자적 확정 + 감사** | `confirm_order()` SQL · `audit_admin_action` | `UPDATE … WHERE status='pending' RETURNING` → 두 번째 승인은 **성립하지 않는다**(중복 지급 원리적 불가) |
| E4 | **구매자 스냅샷 컬럼** | `_DDL` 원문 | `buyer_name`, `buyer_email` 존재. ★그리고 `create_order` 가 **실제로 쓴다**(`public.users.name/email` 스냅샷) |
| E5 | **관리자 목록이 pending 을 포함** | `revenue_service.recent_orders` SQL 원문 | `WHERE o.created_at >= …` — **status 필터 없음** → 승인 대상이 목록에 뜬다 |
| E6 | **남용 경계** | `coin_orders_service.py:37-38` | `PENDING_ORDER_CAP = 5` · `DAILY_ORDER_CAP = 50` |
| E7 | **전상법 §6 보존 규율** | `purge_expired_buyer_pii` | `paid_at IS NULL` 구조적 잠금(#1005 가 그것을 지켰다) |

★**처방이 달라진다**: 「없는 것을 새로 만든다」가 아니라 **「있는 것을 안 쓰는 자리를 배선한다」**.

### 1-B. 실제로 **없는 것** (여기만 만든다)

| # | 없는 것 | 확인 방법 | **결과(실측)** |
|---|---|---|---|
| G1 | **입금 계좌 안내** | 목적 검색 `새마을\|예금주\|계좌번호\|bank_account` (결제 도메인) | **0건**. ★대조군: 같은 조회로 토스 가상계좌 주석 **2건**이 나온다 → 조회기 생존. 사용자는 **어디로 입금할지 모른다** |
| G2 | **실제 입금자명 수집** | `create_order` 원문 | `buyer_name` 은 **가입자명 스냅샷**이다. 회사명·가족 명의로 입금하면 **대사 불가** |
| G3 | **관리자 목록에 입금자명 없음** | `recent_orders` SELECT 절 원문 | `buyer_name` 을 **SELECT 하지 않는다** → 화면이 그 값을 볼 수 없다 |
| G4 | **입금 대기 전용 큐 없음** | 같은 SQL | 전체 혼재 + `LIMIT 30` · `ORDER BY COALESCE(paid_at, created_at) DESC` → 승인 대기가 **묻힌다** |
| G5 | **사용자에게 다음 행동 안내 없음** | `CoinsClient.tsx` pending 행 | 취소 버튼뿐. *"입금하면 된다"* 를 아무도 말하지 않는다 |
| G6 | **결제수단이 단일값** | `resolve_payment_mode()` | `str` 하나 — 카드와 무통장입금을 **동시에 제시할 수 없다** |

### 1-C. 계약 소비처 — ★**파생형으로 셌다**(목록이 곧 상한이 된다)

`git grep 'payment_mode|paymentMode|resolve_payment_mode'` 전수: **백엔드 9곳 · 프론트 15곳 = 24곳**.
그중 **판정에 쓰는 게이트**는 5곳이다:

    routers/billing.py:626  `!= "toss"` → 501 (토스 승인)
    routers/billing.py:678  `!= "toss"` → 501 (토스 환불)
    CoinsClient.tsx:451     `=== "toss"`      (결제창 버튼)
    CoinsClient.tsx:541     `=== "simulated"` (데모 self-confirm)
    CoinsClient.tsx:570     `=== "toss"`      (환불 버튼)

## 2. 변경 내용과 그것이 회귀가 아닌 근거

### 2-1. ★결제수단을 **목록으로** — 그러나 `payment_mode` 는 **파생시킨다**

두 출처를 만들지 않는다(이 저장소가 반복해 데인 형태). 목록이 **유일한 계산처**다:

```python
def resolve_payment_methods(settings) -> list[str]:   # 우선순위 순
    ...
def resolve_payment_mode(settings) -> str:            # ★하위호환 — 목록에서 파생
    m = resolve_payment_methods(settings)
    return m[0] if m else "manual_only"
```

**회귀가 아닌 근거**: 기존 24 소비처가 읽는 `payment_mode` 의 **값이 바뀌지 않는다**.

| 상태 | 종전 `payment_mode` | 새 `payment_methods` | 새 `payment_mode`(파생) |
|---|---|---|---|
| 토스 정상 · 계좌 미설정 | `toss` | `["toss"]` | `toss` ✔동일 |
| 토스 없음 · 계좌 미설정 · 시뮬 on | `simulated` | `["simulated"]` | `simulated` ✔동일 |
| 토스 없음 · 계좌 미설정 · 시뮬 off | `manual_only` | `[]` | `manual_only` ✔동일 |
| **토스 키 있는데 짝 틀림** | `manual_only`(#1005) | `[]` | `manual_only` ✔동일 |
| 계좌 설정됨(신규 상태) | — | `["bank_transfer"]` 또는 `["toss","bank_transfer"]` | `toss` 또는 `bank_transfer` |

★**#1005 가 세운 무료충전 방어를 그대로 옮긴다**: **토스 키가 존재하면 `simulated` 는 후보에서
제외**한다(짝이 틀려도). 그것을 안 옮기면 목록화가 **게이트 우회를 되살린다** —
같은 PR 안에서 자기가 고친 결함을 재발시키는 형태다.

★**`simulated` 는 실수단이 하나도 없을 때만** 후보가 된다(무료 코인 경로와 실결제 경로의 공존 금지).

### 2-2. 계좌 정보는 **관리자 키 금고**를 경유한다 (소유자 결정)

`secret_store.CATALOG` 에 `secret: False` 항목으로 추가 — **토스 클라이언트 키와 같은 통로**다
(그 통로는 관리자 화면이 그룹별로 **자동 렌더**한다 — 새 UI 를 만들지 않는다).

* **git 이력에 계좌·성명이 남지 않는다**(되돌릴 수 없는 노출을 만들지 않는다)
* 은행을 바꿔도 **재배포가 필요 없다**(`set_secret` 이 `os.environ` 에 즉시 반영)
* **미설정이면 무통장입금이 켜지지 않고**, 관리자 화면이 그 사실을 말한다(토스와 같은 규율)

★필수 3항목이 **모두** 있어야 켠다 — 한둘만 있으면 *"어디로 얼마를 보내라"* 가 불완전해지고,
그 상태로 안내하면 **사용자가 엉뚱한 곳에 송금한다**(되돌릴 수 없다).

### 2-3. 입금 대사(reconciliation) 를 가능하게 한다

| 변경 | 왜 |
|---|---|
| `POST /orders` 가 `depositor_name`(선택) 을 받아 `buyer_name` 에 쓴다 | 비우면 **종전대로 가입자명**(회귀 0). 다르게 입금할 사람만 적는다 |
| `recent_orders` SELECT 에 `buyer_name` 추가 | 없으면 화면이 그 값을 **볼 수 없다**(G3) |
| 관리자 화면에 **입금 대기 전용 구역** | 혼재 목록 + `LIMIT 30` 에 묻히지 않게(G4) |
| 사용자 pending 행에 **계좌·금액·입금자명 안내** | *"입금하면 된다"* 를 말하는 곳이 지금 없다(G5) |

★**대사 키는 「입금자명 + 금액 + 주문번호」 셋이다.** 하나로는 동명이인·동일금액에서 갈리지 않는다.
화면이 주문번호를 **입금자명 뒤에 붙이도록** 안내한다(은행 입금자명 길이 제한 안에서).

### 2-4. ★이번에 **하지 않는 것** (사유 포함 — 목록에서 지우지 않는다)

| # | 안 하는 것 | 왜 |
|---|---|---|
| N1 | **미입금 주문 자동 만료** | 스케줄러가 필요하고, 그것은 #1005 §2-4 Q1 과 **같은 축**이다. 사용자는 이미 취소 버튼이 있고 상한이 5건이라 즉시 위험은 아니다. ★단 **미측정**: 실제로 상한에 걸리는 빈도는 안 쟀다 |
| N2 | **입금 자동 대사(펌뱅킹·오픈뱅킹)** | 은행 API 계약이 선행돼야 한다. v1 은 사람이 확인한다(요구가 그것이다) |
| N3 | **무통장입금 환불 자동화** | 계좌 송금은 우리 코드가 할 수 없다. 화면이 *"수동 환불"* 이라고 **말하게** 한다 |
| N4 | `provider` 값을 `"manual"` → `"bank_transfer"` 로 변경 | 기존 행이 `manual` 이라 **매출 집계가 갈린다**(`COALESCE(provider,'(미상)')` 그룹). 이름을 바꾸는 이득보다 분열의 해가 크다 |

## 3. ★검증하지 못한 것 (비워 두지 않는다)

1. **실제 입금 왕복 미측정** — 진짜 송금을 하지 않는다(되돌릴 수 없고, 검증 비용이 보호 대상과 같다).
   대신 **상태 전이**를 태운다: 주문 생성 → 관리자 승인 → 코인 증가. 돈은 움직이지 않는다.
2. **계좌 정보 미등록 상태** — 소유자가 금고에 넣어야 켜진다. 그 전까지 `bank_transfer` 는
   후보에 없다(그것이 설계다). 등록 후 확인 절차는 §6.
3. **PENDING_ORDER_CAP 도달 빈도 미측정**(N1) — 만료를 안 만든 근거가 *"즉시 위험 아님"* 인데
   그 「즉시」를 재지 않았다. ★**미룸의 근거를 실측하지 않았다**고 명시한다.
4. **동시 승인 경쟁 미측정** — `confirm_order` 의 원자성은 SQL 원문으로 **읽었지만**(E3)
   두 관리자가 동시에 누르는 것을 라이브에서 재지는 않았다.

## 4. 되돌리기 경로

- **즉시 무해화**: 관리자 금고에서 계좌 3항목 중 하나만 삭제 → `bank_transfer` 가 후보에서 빠짐
  → 화면에서 사라진다. **배포 불필요.**
- **코드**: revert. 계약은 **추가**(`payment_methods`)이고 기존 `payment_mode` 값은 불변이라
  중간 상태에서도 회귀가 없다(§E-21: 중간 상태가 회귀인지 확인함).
- **데이터**: 스키마 변경 **0**(기존 `buyer_name` 컬럼만 쓴다). 새 테이블 없음.

## 6. 소유자 작업

관리자 > API 키 > **「무통장입금(계좌이체)」** 그룹:

| 항목 | 값 |
|---|---|
| `BANK_TRANSFER_BANK_NAME` | `새마을금고` |
| `BANK_TRANSFER_ACCOUNT_NO` | `9002148908909` |
| `BANK_TRANSFER_HOLDER` | `강재희` |

세 항목이 **모두** 채워지면 충전 화면에 무통장입금이 나타난다. 하나라도 비면 켜지지 않고
관리자 화면이 **무엇이 비었는지** 말한다.

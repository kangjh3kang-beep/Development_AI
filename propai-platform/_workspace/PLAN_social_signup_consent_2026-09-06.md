## 2. 그래서 무엇을 만드는가

★**«간편 회원가입을 만든다»가 아니다 — 이미 된다.** 만들 것은 **그 경로의 동의**다.

| 축 | 지금 | 목표 |
|---|---|---|
| 계정 생성 | ◎ 자동 | 그대로 |
| 테넌트 생성 | ◎ 자동 | 그대로 |
| 비밀번호 | ◎ 요구 안 함 | 그대로(네이버 검수 요건) |
| **동의 수집** | ✘ 없음 | **신규 가입일 때만** 동의 화면 → 서버 기록 |
| **동의 이력** | ✘ 0건 | `UserConsent` 에 이메일 가입과 **동일 형식**으로 |
| 퍼널 관측 | ✘ 0건 | 가입 시작·동의·완료 이벤트 |

### 설계 — 「신규일 때만」이 핵심

기존 사용자의 소셜 **로그인**에 동의 화면을 끼우면 **매번 뜬다**(로그인이 무거워진다).
그래서 `get_or_create_oauth_user` 가 **생성한 경우**와 **찾은 경우**를 구분해 돌려주고,
생성일 때만 콜백 화면이 동의 단계를 그린다.

    ㉠ oauth_common: 반환에 `created: bool` 을 추가(지금은 User 만 돌려준다)
    ㉡ 신규면 동의 미완 상태로 두고, 콜백 화면이 **동의 UI**를 그린다
    ㉢ 동의 제출 → `POST /auth/consents` → 이메일 가입과 **같은 UserConsent 형식**으로 기록
    ㉣ 동의 전에는 보호 자원 접근을 막는다(★그렇지 않으면 동의는 장식이다)

★㉣ 가 없으면 «동의 화면을 그린다»만 남고 **건너뛰어도 아무 일이 안 일어난다**.

## 3. ★검증하지 못한 것

- **프로덕션에 동의 없이 만들어진 소셜 계정이 몇 건인지** — DB 조회 권한이 없어 못 쟀다.
  **이유는 「권한 부족」이다**(사건 미발생도, 장치 부재도 아니다). 소유자에게 올린다.
- 소셜 사용자 `admin` 역할의 **교차 테넌트 위험** — 코드상 자기 테넌트에 한정돼 보이나 **미측정**.
- 기존 소셜 사용자에게 **소급 동의**를 어떻게 받을지 — 법무 판단이 필요하고 내 범위 밖.
- 이 계획의 ㉠~㉣ 는 **아직 한 줄도 구현하지 않았다.** 이 문서는 계획이다.

## 4. 되돌리기

㉠~㉣ 는 독립 커밋으로 쌓는다. ㉣(차단)만 revert 하면 동의는 수집하되 차단은 풀린다.
㉠(반환 형태 변경)은 호출부가 3사 핸들러뿐이라 되돌림 비용이 작다.

## 5. 잠금

- **두 모집단으로** 가른다: 신규 소셜 가입 → `UserConsent` 3행 생성 /
  기존 사용자 재로그인 → **0행 추가**(매번 쌓이면 그것도 결함)
- ★**동의 형식이 이메일 가입과 같은지**를 단언한다 — `consent_type` 집합·`policy_version` 을
  **이메일 경로에서 파생**해 비교(손으로 적으면 두 경로가 조용히 갈린다)
- ㉣ 잠금: 동의 미완 사용자가 보호 자원을 부르면 **거부**되는지. 변이로 그 가드를 지워 CAUGHT 확인
- 회귀 축: 기존 소셜 **로그인**이 느려지거나 동의 화면을 보지 않는지

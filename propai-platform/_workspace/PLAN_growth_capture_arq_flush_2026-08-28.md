## 2. 변경 내용과 **회귀가 아닌 근거**

1. `capture_service.drain_until_empty(session_factory, *, max_rounds=20)` **신설** —
   현재 API 가 **두 곳에서 복제**하고 있는 배수 루프를 **단일 경로**로 추출한다.
   ★상한은 `500` 리터럴이 아니라 **`_FLUSH_LIMIT` 에서 파생**시킨다(P9 교정).
2. `apps/api/main.py` 두 곳이 그 함수를 부르게 **치환**(동작 보존).
3. `apps/worker/main.py` `startup` 에 배수 루프 태스크 기동 · `shutdown` 에 취소 + 마지막 배수.

**회귀가 아닌 근거**: ①API 쪽은 **같은 순서·같은 상한**을 부르는 순수 추출이고
`500 == _FLUSH_LIMIT` 을 테스트로 못 박는다 ②워커 쪽은 **신규 배선**이라 종전 동작이 없다
③`record_event` 는 논블로킹 push 뿐이라 배수 추가가 태스크 경로를 안 바꾼다.

## 3. ★검증하지 못한 것

- **프로덕션 arq 컨테이너가 실제로 초당 몇 건을 쌓는지 — 미측정.** 컨테이너 로그 접근이 없다.
  **코드 경로의 실재만** 보였고 **비용은 미정량**이다. *"유실이 크다"* 고 쓰지 않는다.
- arq 워커가 **현재 프로덕션에 떠 있는지** 직접 확인하지 못했다(간접 근거만:
  `Dockerfile.oracle` 이 `apps/worker` 를 번들 · `scripts/a1-arq-worker.sh` 실재).
  ★**떠 있지 않다면 이 PR 은 유실을 안 줄이고 「미래 대비」다** — 그 경우에도 회귀는 아니다.
- 워커에서 `AsyncSessionLocal` 이 API 와 **같은 DB 를 가리키는지** 런타임 확증은 못 했다
  (`startup` 이 그것을 주입하고 있으므로 **구조상 같다**는 것까지만).
- **동시 배수**(API·워커·Celery 가 각자 자기 큐를 비운다)는 큐가 프로세스 로컬이라
  **경합하지 않는다** — 다만 `platform_events` **INSERT 동시성**은 재보지 않았다
  (`ON CONFLICT DO NOTHING` 이 있으므로 안전하다고 **추정**).

## 4. 되돌리기 경로

단일 커밋 revert. 워커 배선은 `startup` 안의 `try/except` 로 감싸 **실패해도 워커가 죽지 않는다**.
API 치환은 순수 추출이라 revert 시 원문으로 복귀한다.

## 5. 잠금 — ★**층을 먼저 적는다**

| 층 | 락 |
|---|---|
| 순수함수 | `drain_until_empty` 가 큐를 비운다 · `max_rounds` 상한에서 멈춘다(두 모집단) |
| 상수 파생 | `500` 리터럴이 **어디에도 없다** · 상한이 `_FLUSH_LIMIT` 에서 나온다 |
| **배선(★핵심)** | **파생형** — 진입점의 임포트 폐포가 `record_event` 에 닿으면 **그 진입점은 배수해야 한다.** 새 진입점이 생겨도 자동 감시 |
| 워커 배선 | `WorkerSettings.on_startup` 이 배수 태스크를 건다 · `on_shutdown` 이 마지막 배수를 한다 |
| 종료 안전 | 워커 종료 시 취소가 유실로 가지 않는다(#920 의 `_requeue` 계약 재사용) |

★**배선 락이 이 PR 의 값어치다.** 함수만 잠그면 *"만들었는데 아무도 안 부른다"* 가
그대로 재발한다 — 이 결함이 정확히 그것이었다.

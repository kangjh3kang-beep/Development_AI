## 3. ★검증하지 못한 것

1. **배포 후 실제 커버리지 변화 미확인** — 배치로 도는 기능이라 **배치 1회 실행 후**에만
   확인된다(`analyze-growth-hourly` = 매시 05분). 배포 착지는 검증이 아니다.
2. **5xx 경로는 합성 입력으로만 태웠다** — 라이브 7일 5xx 가 0건이라 실데이터 확인 불가.
3. **`api_error` 이벤트는 안 봤다** — 프론트는 4xx/5xx 를 `api_error` 로 따로 쏜다.
   이 필터는 `api_call`·`llm_call` 만 건드린다. 두 계측의 관계는 **미측정**.
4. **baseline 자기참조 · tenant 혼입(62배) · n=20 p95 잡음(회귀 없이 발화 23~36%)**
   — 전부 **미해결**이고 이 PR 은 손대지 않는다. 섞어 읽으면 *"고쳤는데 그대로"* 가 된다.
5. **30일 replay 는 내 재구현**이다 — 실제 배치를 돌린 것이 아니라 같은 술어를 SQL 로 흉내 냈다.
6. ★**전환 1배치에서 오탐이 난다**(리뷰 F2). baseline 이 **직전 배치 자기 p95**(P10)라,
   배포 직후 첫 배치는 `정제 p95` vs `정제 전 baseline` 을 비교한다. 리뷰 실측으로
   비교가능 95 key-hour 중 발화 **24 → 27**, **신규 오탐 3건**
   (`/ai/status` ×1.96 · `/zoning/parcel-boundaries` ×1.76, ×1.54). **봉합하지 않았다** —
   1배치(1시간)만 지속되고, 봉합하려면 전환 플래그를 들여야 하는데 그 복잡도가 더 크다.
   ★**배포 후 첫 시간의 `latency_regression` 급증은 회귀가 아니라 이 전환 효과다.**
7. ★**백엔드 관측 4xx 가 어떤 검출기에도 없어진다**(리뷰 F7). `_analyze_error_cluster`
   (`analyzer.py:536`)는 `event_type IN ('js_error','api_error')` 만 읽고, 백엔드는 4xx 를
   `api_call` 로 쓴다. **프론트가 본 4xx 는 `api_error` 로 가므로 완전 실명은 아니다**
   (7일 415건) — 그러나 **백엔드-only 4xx 의 규모는 미측정**이다. 별건 부채.
8. **전건 4xx 인 진짜 라우트**는 지연을 못 보게 된다(오늘은 표본 1건이라 어차피 하한 미달).

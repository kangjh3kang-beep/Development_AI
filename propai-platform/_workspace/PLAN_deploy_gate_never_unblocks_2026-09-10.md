## 2. 변경 내용과 **회귀가 아닌 근거**

### 2-a. push 기본 타깃 `both` → `web`

```yaml
DEPLOY_TARGET: ${{ github.event.inputs.target || 'web' }}
```

회귀가 아닌 근거: `workflow_dispatch` 의 **명시 선택은 그대로**다(`both`·`api` 여전히 선택 가능).
바뀌는 것은 **인자가 없을 때의 기본값**뿐이고, 그 기본값이 향하는 서버(158)에서는
`both` 가 **P8 로 금지된 상태**다. 즉 이 변경은 **도달 불가능하던 잘못된 기본값**을
**운영 관행(P10)과 일치**시킨다.

### 2-b. ★**`on: push` 를 지운다** — 처방을 「증명 가능한 것」으로 바꿨다

초판은 `cancel-in-progress: true` **만으로** 고치려 했다. **하중 전제가 미검증이었다**(P13):
GitHub 이 `waiting` 실행을 concurrency 로 취소하지 **않으면 이 PR 은 아무것도 고치지 못한다.**

그래서 축을 바꾼다 — **실행 생성원을 없앤다.** 자동 트리거가 없으면 누적이 **원리적으로**
불가능하고, 이는 **트리거 정의만으로 성립**한다(플랫폼 의미론을 추측하지 않는다).

회귀가 아닌 근거: 푸시 트리거의 **측정된 편익은 0**(400건 성공 0)이고, 지금은 **성공할 수도
없다**(P11 시크릿 미등록). 실제 배포 경로인 통합자의 수동 `safe-deploy.sh web main` 과
`workflow_dispatch` 는 **그대로 살아 있다**. ★되살리는 4단계를 워크플로 주석에 적었다 —
지우기만 하고 길을 안 남기면 그게 더 나쁘다.

### 2-c. `cancel-in-progress: false` → `true` (보조)

교착을 푸는 것은 2-b 다. 이 값은 **묵은 dispatch 대기**에 대한 보조 방어다.

★**위험의 분모를 고쳐 적는다.** 초판은 *"그 창에 들어간 실행은 100건 중 0건"* 이라 썼는데
**그 0 은 배포가 한 번도 돌지 못했기 때문**이다 — ***폐지하려는 체제의 통계로 폐지 후의
위험을 계산했다***(§증거규율 5). 올바른 분모로 재면 푸시 간격 **중앙값 23.1분** vs 실행
소요 **22~28분** ⇒ 푸시가 살아 있었다면 **과반이 절단**된다. **푸시를 지웠으므로** 남은
생성원은 수동 dispatch 뿐이고 그 간격은 시간 단위라 창이 사실상 닫힌다.

★**0 은 아니다**: 배포 중 두 번째 dispatch 를 누르면 `safe-deploy.sh:195` 의
`docker stop; docker rm` ~ `:196` `compose up -d` 사이에서 **158 이 뜬다**.
복구는 `bash propai-platform/scripts/rollback-web.sh`(§4).

### 2-d. dispatch 드롭다운 기본값 `both` → `web`

★**형제 축이었다.** env 폴백만 고치면 **사람이 실제로 누르는 값**은 그대로 `both` 다
(실측: 그 줄을 바꾸는 변이가 **SURVIVED**). 이 저장소가 6연속 반복한 결함 클래스다.

### 2-e. ★대안 비교 (초판에 **0건**이었다 — 채택안이 최선임을 보이는 문장이 없었다)

| 대안 | 편익 | 비용·기각 사유 |
|---|---|---|
| **(채택) `on: push` 제거** | 누적 원리적 불가 · **트리거 정의만으로 증명** | 자동배포 능력 상실 — 단 **측정 편익 0/400** 이고 되살리는 길을 주석에 남겼다 |
| `cancel-in-progress: true` 단독 | 코드 2줄 | ★**하중 전제 미검증**(P13). 거짓이면 **효과 0 · 절단 위험만 도입** |
| 원격 분리실행(`setsid …&`) + 상태 폴링 | 절단이 **원리적으로** 불가 | ★**검증 불가** — 시크릿·ssh 가 없어 이 세션에서 한 줄도 태울 수 없다. 못 태우는 배포 스텝을 크게 고치는 것은 이 PR 의 위험을 키운다. **별건 후보로 §3 에 남긴다** |
| 잡 단위 concurrency 분할 | 게이트 잡만 격리 | 배포 상호배제가 깨진다(동시 배포 허용) — 더 나쁘다 |

### 2-c. ★하지 않는 것

- **`required_reviewers` 보호규칙을 건드리지 않는다** — 저장소 설정이지 코드가 아니다(권한 밖).
- **`api`·`both` 를 dispatch 선택지에서 지우지 않는다** — ★**사유를 정정한다**(P12).
  초판의 *"168 경로 · preflight 모집단"* 은 **거짓**이었다. 남기는 진짜 이유는 하나뿐이다:
  158 에서 api 이미지를 굽는 **디버그 경로**가 필요할 수 있다(트래픽은 0이다).
  **기본값에서 뺐으므로 실수로 밟히지 않는다.**

## 3. ★검증하지 못한 것

1. ★★**`cancel-in-progress: true` 가 `waiting`(승인 대기) 실행을 취소하는지 미측정**(P13).
   초판은 **이것이 하중 전제인 줄도 몰랐다.** 지금은 처방이 2-b(푸시 제거)라 **하중을 받지
   않지만**, 되살릴 때 필요하다. **재측정 명령**(값이 아니라 방법을 적는다 · §28):

   ```bash
   # push 를 되살린 뒤, main 에 2분 간격으로 두 번 푸시하고:
   gh run list --workflow="Deploy to Oracle Cloud" --limit 3 \
     --json databaseId,status,conclusion,createdAt,updatedAt
   # 판정: 첫 실행이 waiting 인 상태에서 둘째 실행 created_at 의 ±5초 안에
   #       첫 실행이 cancelled 로 뒤집히면 → 전제 참
   #       뒤집히지 않고 둘째가 pending 이 되면 → 전제 거짓
   ```

2. **고친 뒤 배포가 성공하는지 미측정** — **선행이 시크릿 등록**(P11)이고 그건 사용자 몫이다.
   ★「고쳤다」와 「고친 것이 배포를 성공시킨다」는 다른 명제다. 이 PR 은 앞의 것만 주장한다.

3. **절단 위험은 0이 아니다**(§2-c) — 배포 중 두 번째 dispatch. 창은 좁아졌지만 남았다.
   ★완전 해소는 **원격 분리실행 + 상태 폴링**인데 **이 세션에서 검증 불가**(ssh·시크릿 없음).
   별건 후보.

4. **`required_reviewers` 가 2026-08-20 직전에 켜진 것으로 보이나 확증 못 했다**
   (GitHub 이 보호규칙 편집에 `updated_at` 을 안 올린다). **왜 그때 켜졌는지**가 이 처방이
   사용자 의도와 맞는지를 가른다 — 사용자에게 물어야 한다.

5. **승인 게이트는 사람 1인**(`can_admins_bypass: true` · 리뷰어 = 소유자 1인). 자동 트리거를
   되살리면 **매 머지마다 소유자가 눌러야** 나간다 — 교착이 **경쟁**으로 바뀔 뿐이다.

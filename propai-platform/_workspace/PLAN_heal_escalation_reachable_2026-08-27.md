## §1 전제 표 (★결과 칸은 **실측값**이다 · 측정 2026-08-27 10:5x~11:1x KST)

### A. 라이브 — 에스컬레이션은 한 번도 발화한 적이 없다

| 전제 | 확인 방법 | 결과 |
|---|---|---|
| `heal_escalation` 이 존재하지 않는다 | `/growth/insights?insight_type=heal_escalation&limit=1` 의 `total` | **0** |
| 〃 상태별로도 0 | `&status=open` / `&status=acted` | **0 / 0** |
| ★**양성 대조군**(조회기 생존) | `insight_type=fallback_rate` | **26** |
| ★**음성 대조군**(판별력) | `insight_type=zzz_not_a_type` | **0** |
| 치유는 실제로 돈다 | `/growth/heal-log` 의 `total` | **520** |

★**절단 주의**: 처음에 `insights?limit=500`(전체 `total=3263`) 으로 재고 *"heal_escalation 0"* 이라 쓸 뻔했다.
그건 **최신 500 안에서 0** 일 뿐이다. **타입 필터로 다시 재서** 전수 0 을 확인했다.

### B. 왜 0인가 — 카운터의 **천장이 임계보다 낮다**

`should_escalate(trigger_count) := trigger_count >= ESCALATION_THRESHOLD(5)` 인데,
`trigger_count` 는 `_guard_counts` 가 **`heal_action` 이벤트(=실행된 것만)** 를 센 값이다.
그리고 `_cap_exceeded(count, cap) := count >= cap` 이 **실행을 막는다.**
→ 실행이 막히면 이벤트가 안 생기고, 그래서 **`trigger_count` 는 `t_cap` 을 넘을 수 없다.**

| action_type | `t_cap` | 도달 가능한 최대 `trigger_count` | `>=5` 가능? |
|---|---|---|---|
| `cache_warm` | 1 | 1 | **✗** |
| `threshold_relax` | 2 | 2 | **✗** |
| `stale_reanalysis` | 3 | 3 | **✗** |
| `circuit_observe` | 10 | 10 | ◎ |

★**도달 가능한 유일한 액션이 `circuit_observe`** 이고, 그 액션의 코드 주석은 스스로를
*"관측 기록(부작용 없음)"* 이라 적는다 — **에스컬레이션이 필요 없는 것만 에스컬레이션할 수 있다.**

**라이브 재현(인계서 드라이런을 제가 다시 뜬 값 — 수치 일치)**:
```
heal-log 표본 500 (total 520) · 시간버킷 조합 472개
  캡 도달(>=t_cap) : 24/472 = 5.1%
  임계 도달(>=5)   :  0/472 = 0.0%    ← 현행 escalate 조건
  캡 도달 상위: threshold_relax fallback_rate:site_analysis 18회 · fallback_rate:feasibility 3회
```

### C. ★인계서의 **메커니즘 기술은 틀렸다**(결론은 옳다 — 승계하지 않고 재서 확인)

인계서 §3: *"차단된 후보는 `continue` 로 `execute()` 앞에서 빠져 **이벤트를 안 남긴다**"* → 이 부분은 맞다.
그러나 이어지는 *"그래서 에스컬레이션을 못 한다"* 는 **틀렸다.**

`evaluate()` 실측 — `_escalate` 호출은 **차단 `continue` 보다 앞에 있다**:
```
if decision["escalate"]:  await _escalate(...)      ← 먼저
if not decision["allow"]: ...; continue             ← 나중
```
즉 **차단된 후보도 에스컬레이션은 평가된다.** 진짜 원인은 오직 **§1-B 의 카운터 천장**이다.
→ 처방이 달라진다: *"차단 경로에서 escalate 를 부르게 하자"* 는 **이미 되어 있으므로 무의미**하고,
  고칠 것은 **무엇을 세는가** 하나뿐이다.

### D. 하류 — 발화시키면 무엇이 일어나나

| 전제 | 확인 방법 | 결과 |
|---|---|---|
| `_escalate` 에 **중복 억제가 없다** | 함수 본문 — 조건 없는 `INSERT` | **없음(확인)** |
| 발화 시 `recommended_action` | `_escalate` 리터럴 | `propose_pr` |
| `propose_pr` 이 위험한가 | `growth_pr_task.py` — `GH_TOKEN` 부재 시 | `artifact_only`(마킹만) *(인계서 실측 승계 — 제가 재확인하지 못함, §3 참조)* |

★**중복 억제가 없는데 §1-B 의 상위 조합이 18회**다 → 억제 없이 발화시키면 **한 트리거가 화면을 채운다.**
그래서 **억제는 선택이 아니라 이 변경의 일부**다.

### E. 치유 루프 자체의 생존 — ★**내 변경이 발화할 수 있는 상태인가**

이 절이 없으면 §0 이 인용한 그 교훈(*"발화한 적 없는 안전망"*)을 **내가 그대로 반복**한다.

| 관측 | 값 |
|---|---|
| 최신 **인사이트** | `2026-08-27T01:05Z` — **1.1시간 전** (analyzer 생존) |
| 최신 **heal 액션** | `2026-08-24T18:50Z` — **55.3시간 전** |
| beat 등록 | 배포 로그 `Verify registered tasks` 에 `evaluate_healing` **등재 확인** |

→ **스케줄러는 살아 있고 heal 만 조용하다.** 이 침묵은 두 얼굴이다:
**H1 고칠 것이 없다**(정상) / **H2 후보 도출이 죽었다**(결함).
★**본 계획은 H1/H2 를 가르지 않는다** — 가르지 않아도 변경은 옳지만,
**"고쳤으니 곧 발화한다"고 말할 수는 없다.** §3 에 미측정으로 싣는다.

## §2 변경 내용과 **회귀가 아닌 근거**

### 무엇을 바꾸나 — **세는 대상**만 바꾼다

**상수는 건드리지 않는다**(§0 기각 근거):
`ESCALATION_THRESHOLD` · `PER_TRIGGER_HOURLY_CAP` · `GLOBAL_HOURLY_CAP` · `COOLDOWN_MIN` **전부 불변**.

바꾸는 것: 에스컬레이션의 입력을 **「실행된 횟수」 → 「캡에 막힌 시도 횟수」** 로.

```
현행:  should_escalate(실행수)        천장 = t_cap  <  5   → 영원히 거짓
변경:  should_escalate(캡차단 시도수)  천장 = 없음          → 도달 가능
```

**의미가 더 옳다**: 에스컬레이션의 뜻은 *"자동치유가 반복됐는데 효과가 없다"* 이다.
캡에 막히고 있다는 것은 **같은 트리거가 계속 치유를 원하는데 못 하고 있다**는 뜻이므로,
*"사람이 봐야 한다"* 의 신호로 **실행 횟수보다 직접적**이다.

### ★쿨다운 차단은 세지 않는다 (과잉 발화 방지)

`gate()` 는 **쿨다운을 캡보다 먼저** 판정하고 즉시 반환한다. 따라서 쿨다운 차단은
캡 차단 카운터에 **구조적으로 들어올 수 없다.** 이는 우연이 아니라 이 설계가 의존하는 성질이며,
**락으로 고정한다**(§5-L4). 쿨다운(정상 페이싱)까지 세면 `threshold_relax`(쿨다운 15분 · beat 10분)가
**상시 에스컬레이션**된다.

### 중복 억제 — **축 단위 1건**

같은 `(action_type, trigger_key)` 에 대해 **열린 `heal_escalation` 이 이미 있으면 새로 만들지 않는다.**
(§1-D 의 18회가 18줄이 되지 않게.) 억제는 **`open` 만** 본다 — 사람이 `dismissed` 한 뒤
문제가 재발하면 **다시 올라와야** 하기 때문이다(한쪽만 거는 경계 금지 · §D-19).

### 회귀가 아닌 근거

1. **상수 불변** → 실행 정책(무엇이 언제 실행되는가)이 **전혀 바뀌지 않는다.**
   `allow` 판정 경로에 손대지 않으므로 **치유 동작 자체는 바이트 동일**하다.
2. 새 카운트는 **새 이벤트 타입**에 기록한다 → 기존 `heal_action` 집계·화면·`_guard_counts` 무영향.
3. 현행 라이브에서 `escalated` 는 **0** 이므로(§1-A) **줄어들 수 있는 값이 없다** — 단조 증가 방향뿐이다.
4. `_escalate` 는 `best-effort`(예외 삼킴)이고 호출부도 그렇다 → 실패가 치유 사이클을 죽이지 않는다.

## §3 ★검증하지 **못한** 것 (비워 두지 않는다)

1. **H1/H2 를 가르지 못했다**(§1-E). heal 액션이 55시간째 없는 것이 *"고칠 게 없어서"* 인지
   *"후보 도출이 죽어서"* 인지 **미측정**이다. → **이 변경이 언제 처음 발화할지 예측하지 않는다.**
   *(가르는 법: `_candidate_actions` 의 입력이 되는 open 인사이트가 실제로 있는지 + heal 태스크의
   마지막 실행 시각 — `growth_last_run.heal` 플래그 값이 `null` 로 보이는데 그 자체가 별건 의심점이다.)*
2. **`propose_pr` 의 실제 하류 동작을 제가 재지 못했다.** 인계서가 `artifact_only` 라고 적었고
   그럴듯하나, **저는 남의 측정을 승계했을 뿐**이다(§증거 규율 7). 억제를 넣으므로 폭주 위험은
   낮지만, **"안전하다"고 단정하지 않는다.**
3. **라이브 발화 확증 없음.** 배포 후에도 조건이 오지 않으면 발화하지 않는다 — 그것은 정상이며,
   **발화 0 을 「고쳐지지 않았다」로 읽지 말 것.** 판정은 **락**과 **드라이런**으로 한다.
4. ~~`threshold_autotune` 이 세 캡 딕셔너리 어디에도 없다~~ → ★**제 오측이었다. 정정한다.**
   `healing_rules.py` 만 grep 해서 내린 결론이었는데, **`feature_flags.py:568~575` 가 임포트
   시점에 `setdefault` 로 등록**하고 있었다(`threshold_autotune` g=2·**t=1**·cd=60 ·
   `feature_toggle` 2/2/30 · `prompt_ab_adopt` 2/1/360). 즉 최다 액션도 **명시 정책 하에** 돈다.
   ★**어떻게 잡혔나**: 이 오측은 제가 다시 재서가 아니라 **락이 잡았다** — 상수 단언이
   형제 테스트와 함께 돌 때만 깨졌고(사전이 임포트로 확장됨), 그 순서 의존을 좇다 드러났다.
   ★**남는 진짜 사실**: 확장된 7종 전부 `t_cap < 5` 이므로 **실행수로 도달 가능한 것은
   여전히 `circuit_observe` 하나뿐**이다 — §1-B 의 결론은 **더 넓은 모집단에서도 성립**한다.
   (이 성질을 `test_the_original_defect_shape_is_documented_by_the_caps` 가 전수로 잠갔다.)

## §4 되돌리기 경로

이 PR 만 `revert`. 상수·실행 경로 무변경이므로 되돌려도 **치유 동작은 그대로**이고,
에스컬레이션이 다시 발화 불가 상태로 **돌아갈 뿐**이다(현행과 동일 = 라이브 0건).
새 이벤트 타입 행이 남지만 기존 조회는 `event_type` 으로 필터하므로 무영향.

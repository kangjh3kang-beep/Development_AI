## §1 전제 표 (★결과 칸은 **실측값**이다 · 측정 2026-08-27 10:5x~11:1x KST)

### A. 라이브 — 에스컬레이션은 한 번도 발화한 적이 없다

| 전제 | 확인 방법 | 결과 |
|---|---|---|
| `heal_escalation` 이 존재하지 않는다 | `/growth/insights?insight_type=heal_escalation&limit=1` 의 `total` | **0** |
| 〃 상태별로도 0 | `&status=open` / `&status=acted` | **0 / 0** |
| ★**양성 대조군**(조회기 생존) | `insight_type=fallback_rate` | **26** |
| ★**음성 대조군**(판별력) | `insight_type=zzz_not_a_type` | **0** |
| 치유는 실제로 돈다 | `/growth/heal-log` 의 `total` | **520** |

★**절단 주의**: 처음에 `insights?limit=500`(전체 `total=3263`) 으로 재고 *"heal_escalation 0"* 이라 쓸 뻔했다.
그건 **최신 500 안에서 0** 일 뿐이다. **타입 필터로 다시 재서** 전수 0 을 확인했다.

### B. 왜 0인가 — 카운터의 **천장이 임계보다 낮다**

`should_escalate(trigger_count) := trigger_count >= ESCALATION_THRESHOLD(5)` 인데,
`trigger_count` 는 `_guard_counts` 가 **`heal_action` 이벤트(=실행된 것만)** 를 센 값이다.
그리고 `_cap_exceeded(count, cap) := count >= cap` 이 **실행을 막는다.**
→ 실행이 막히면 이벤트가 안 생기고, 그래서 **`trigger_count` 는 `t_cap` 을 넘을 수 없다.**

| action_type | `t_cap` | 도달 가능한 최대 `trigger_count` | `>=5` 가능? |
|---|---|---|---|
| `cache_warm` | 1 | 1 | **✗** |
| `threshold_relax` | 2 | 2 | **✗** |
| `stale_reanalysis` | 3 | 3 | **✗** |
| `circuit_observe` | 10 | 10 | ◎ |

★**도달 가능한 유일한 액션이 `circuit_observe`** 이고, 그 액션의 코드 주석은 스스로를
*"관측 기록(부작용 없음)"* 이라 적는다 — **에스컬레이션이 필요 없는 것만 에스컬레이션할 수 있다.**

**라이브 재현(인계서 드라이런을 제가 다시 뜬 값 — 수치 일치)**:
```
heal-log 표본 500 (total 520) · 시간버킷 조합 472개
  캡 도달(>=t_cap) : 24/472 = 5.1%
  임계 도달(>=5)   :  0/472 = 0.0%    ← 현행 escalate 조건
  캡 도달 상위: threshold_relax fallback_rate:site_analysis 18회 · fallback_rate:feasibility 3회
```

### C. ★인계서의 **메커니즘 기술은 틀렸다**(결론은 옳다 — 승계하지 않고 재서 확인)

인계서 §3: *"차단된 후보는 `continue` 로 `execute()` 앞에서 빠져 **이벤트를 안 남긴다**"* → 이 부분은 맞다.
그러나 이어지는 *"그래서 에스컬레이션을 못 한다"* 는 **틀렸다.**

`evaluate()` 실측 — `_escalate` 호출은 **차단 `continue` 보다 앞에 있다**:
```
if decision["escalate"]:  await _escalate(...)      ← 먼저
if not decision["allow"]: ...; continue             ← 나중
```
즉 **차단된 후보도 에스컬레이션은 평가된다.** 진짜 원인은 오직 **§1-B 의 카운터 천장**이다.
→ 처방이 달라진다: *"차단 경로에서 escalate 를 부르게 하자"* 는 **이미 되어 있으므로 무의미**하고,
  고칠 것은 **무엇을 세는가** 하나뿐이다.

### D. 하류 — 발화시키면 무엇이 일어나나

| 전제 | 확인 방법 | 결과 |
|---|---|---|
| `_escalate` 에 **중복 억제가 없다** | 함수 본문 — 조건 없는 `INSERT` | **없음(확인)** |
| 발화 시 `recommended_action` | `_escalate` 리터럴 | `propose_pr` |
| `propose_pr` 이 위험한가 | `growth_pr_task.py` — `GH_TOKEN` 부재 시 | `artifact_only`(마킹만) *(인계서 실측 승계 — 제가 재확인하지 못함, §3 참조)* |

★**중복 억제가 없는데 §1-B 의 상위 조합이 18회**다 → 억제 없이 발화시키면 **한 트리거가 화면을 채운다.**
그래서 **억제는 선택이 아니라 이 변경의 일부**다.

### E. 치유 루프 자체의 생존 — ★**내 변경이 발화할 수 있는 상태인가**

이 절이 없으면 §0 이 인용한 그 교훈(*"발화한 적 없는 안전망"*)을 **내가 그대로 반복**한다.

| 관측 | 값 |
|---|---|
| 최신 **인사이트** | `2026-08-27T01:05Z` — **1.1시간 전** (analyzer 생존) |
| 최신 **heal 액션** | `2026-08-24T18:50Z` — **55.3시간 전** |
| beat 등록 | 배포 로그 `Verify registered tasks` 에 `evaluate_healing` **등재 확인** |

→ **스케줄러는 살아 있고 heal 만 조용하다.** 이 침묵은 두 얼굴이다:
**H1 고칠 것이 없다**(정상) / **H2 후보 도출이 죽었다**(결함).
★**본 계획은 H1/H2 를 가르지 않는다** — 가르지 않아도 변경은 옳지만,
**"고쳤으니 곧 발화한다"고 말할 수는 없다.** §3 에 미측정으로 싣는다.

## §2 변경 내용과 **회귀가 아닌 근거**

### 무엇을 바꾸나 — **세는 대상**만 바꾼다

**상수는 건드리지 않는다**(§0 기각 근거):
`ESCALATION_THRESHOLD` · `PER_TRIGGER_HOURLY_CAP` · `GLOBAL_HOURLY_CAP` · `COOLDOWN_MIN` **전부 불변**.

바꾸는 것: 에스컬레이션의 입력을 **「실행된 횟수」 → 「캡에 막힌 시도 횟수」** 로.

```
현행:  should_escalate(실행수)        천장 = t_cap  <  5   → 영원히 거짓
변경:  should_escalate(캡차단 시도수)  천장 = 없음          → 도달 가능
```

**의미가 더 옳다**: 에스컬레이션의 뜻은 *"자동치유가 반복됐는데 효과가 없다"* 이다.
캡에 막히고 있다는 것은 **같은 트리거가 계속 치유를 원하는데 못 하고 있다**는 뜻이므로,
*"사람이 봐야 한다"* 의 신호로 **실행 횟수보다 직접적**이다.

### ★쿨다운 차단은 세지 않는다 (과잉 발화 방지)

`gate()` 는 **쿨다운을 캡보다 먼저** 판정하고 즉시 반환한다. 따라서 쿨다운 차단은
캡 차단 카운터에 **구조적으로 들어올 수 없다.** 이는 우연이 아니라 이 설계가 의존하는 성질이며,
**락으로 고정한다**(§5-L4). 쿨다운(정상 페이싱)까지 세면 `threshold_relax`(쿨다운 15분 · beat 10분)가
**상시 에스컬레이션**된다.

### 중복 억제 — **축 단위 1건**

같은 `(action_type, trigger_key)` 에 대해 **열린 `heal_escalation` 이 이미 있으면 새로 만들지 않는다.**
(§1-D 의 18회가 18줄이 되지 않게.) 억제는 **`open` 만** 본다 — 사람이 `dismissed` 한 뒤
문제가 재발하면 **다시 올라와야** 하기 때문이다(한쪽만 거는 경계 금지 · §D-19).

### 회귀가 아닌 근거

1. **상수 불변** → 실행 정책(무엇이 언제 실행되는가)이 **전혀 바뀌지 않는다.**
   `allow` 판정 경로에 손대지 않으므로 **치유 동작 자체는 바이트 동일**하다.
2. 새 카운트는 **새 이벤트 타입**에 기록한다 → 기존 `heal_action` 집계·화면·`_guard_counts` 무영향.
3. 현행 라이브에서 `escalated` 는 **0** 이므로(§1-A) **관측상 줄어들 수 있는 값이 없다.**
   ★**정정(독립 리뷰 MINOR-6)**: 종전에 여기 *"단조 증가 방향뿐이다"* 라고 적었는데
   **구조적으로는 거짓**이다. `circuit_observe` 는 종전 설계에서 **유일하게 도달 가능**했고
   (실행수 5~9), 변경 후에는 캡차단이 생기지 않아 **도달 불가**가 된다. 라이브 발화가
   0 이었으므로 **관측상** 회귀는 없지만, 근거를 "구조"로 쓰면 틀린 문장이다.
4. `_escalate` 는 `best-effort`(예외 삼킴)이고 호출부도 그렇다 → 실패가 치유 사이클을 죽이지 않는다.

## §3 ★검증하지 **못한** 것 (비워 두지 않는다)

1. ~~H1/H2 를 가르지 못했다~~ → ★**갈랐다(2026-08-27 11:5x 라이브 실측).** 결론은
   **H1 도 H2 도 아니고 "후보가 구조적으로 비어 있다"** 이다.

   `_candidate_actions` 는 ①최근 **2시간** ②`status='open'` ③`recommended_action IN
   ('heal','none','correct')` 인 인사이트를 읽고, 그중 **`fallback_rate` · `stale_reanalysis`
   두 타입에만 분기**를 갖는다(다른 타입은 SQL 은 통과하나 `for` 루프에 자리가 없다).

   | 관측 | 값 |
   |---|---|
   | 최근 2시간 open 인사이트 | **2건** — 전부 `latency_baseline` (`recommended_action='none'`) |
   | 그중 분기 보유 타입(`fallback_rate`/`stale_reanalysis`) | **0건** |
   | 대조군 — 전 기간 open 중 SQL 통과 | **494건** (조회기 생존) |
   | 그중 분기 보유 타입 | **1건** |

   → **치유 루프는 죽지 않았다. 돌면서 매번 후보 0 을 얻는다.** 생산되는 인사이트가
   `latency_baseline`/`latency_regression` 일색인데 그 타입엔 heal 분기가 없기 때문이다.

   ★**이 변경에 대한 함의를 정직하게 적는다**: 후보가 0 이면 **차단도 0** 이고,
   따라서 **이 수정도 지금 트래픽 구성에서는 발화하지 않는다.** 수정은 옳지만 **잠복**이다.
   *"고쳤으니 곧 critical 이 뜬다"* 고 말할 수 없다 — **그렇게 말하면 §0 이 인용한 그 교훈
   (「존재 ≠ 발화」)을 내가 그대로 반복하는 것이다.**

   ★**별건으로 남긴다**(본 PR 범위 밖): 최다 생산 타입에 heal 분기가 없다는 사실 자체가
   피드백 고리의 더 앞쪽 결함일 수 있다. 다만 *"분기를 추가해야 한다"* 는 **주장이 아니다** —
   `latency_baseline` 은 하한이 없어 소음이 많고(open 3,192 중 72%가 `latency_regression`,
   20%가 `latency_baseline` — 볼트 2026-08-27 문서), 거기에 자동 치유를 붙이는 것은
   **별도의 설계 판단**이다.
2. **`propose_pr` 의 실제 하류 동작을 제가 재지 못했다.** 인계서가 `artifact_only` 라고 적었고
   그럴듯하나, **저는 남의 측정을 승계했을 뿐**이다(§증거 규율 7). 억제를 넣으므로 폭주 위험은
   낮지만, **"안전하다"고 단정하지 않는다.**
3. **라이브 발화 확증 없음.** 배포 후에도 조건이 오지 않으면 발화하지 않는다 — 그것은 정상이며,
   **발화 0 을 「고쳐지지 않았다」로 읽지 말 것.** 판정은 **락**과 **드라이런**으로 한다.
4. ~~`threshold_autotune` 이 세 캡 딕셔너리 어디에도 없다~~ → ★**제 오측이었다. 정정한다.**
   `healing_rules.py` 만 grep 해서 내린 결론이었는데, **`feature_flags.py:568~575` 가 임포트
   시점에 `setdefault` 로 등록**하고 있었다(`threshold_autotune` g=2·**t=1**·cd=60 ·
   `feature_toggle` 2/2/30 · `prompt_ab_adopt` 2/1/360). 즉 최다 액션도 **명시 정책 하에** 돈다.
   ★**어떻게 잡혔나**: 이 오측은 제가 다시 재서가 아니라 **락이 잡았다** — 상수 단언이
   형제 테스트와 함께 돌 때만 깨졌고(사전이 임포트로 확장됨), 그 순서 의존을 좇다 드러났다.
   ★**남는 진짜 사실**: 확장된 7종 전부 `t_cap < 5` 이므로 **실행수로 도달 가능한 것은
   여전히 `circuit_observe` 하나뿐**이다 — §1-B 의 결론은 **더 넓은 모집단에서도 성립**한다.
   (이 성질을 `test_the_original_defect_shape_is_documented_by_the_caps` 가 전수로 잠갔다.)

## §4 되돌리기 경로

이 PR 만 `revert`. 상수·실행 경로 무변경이므로 되돌려도 **치유 동작은 그대로**이고,
에스컬레이션이 다시 발화 불가 상태로 **돌아갈 뿐**이다(현행과 동일 = 라이브 0건).
새 이벤트 타입 행이 남지만 기존 조회는 `event_type` 으로 필터하므로 무영향.

| **L5** | **중복 억제** — 같은 축 2회 차단에 인사이트는 **1건** | 개수 단언 |
| **L6** | ★**억제가 은신처가 되지 않게** — `dismissed` 뒤 재발하면 **다시 올라온다** | L5 의 반대 방향 |
| **L7** | **실행 경로 무변경** — `allow` 판정이 종전과 동일 | 회귀 락 |

★**L3 주의**(메모리 교훈): `limit == QUOTA_LIMIT_UNKNOWN` 류의 **자기 상수 단언**은 상수를 바꾸면
같이 바뀌어 **정반대 값도 통과**한다. **리터럴 `5`·`{1,2,3,10}` 으로 못 박는다.**
★**변이는 함수 안에만 넣지 않는다**(메모리 교훈): **호출부(배선)** 에도 넣어 `evaluate` 가
그 카운터를 **실제로 쓰는지**까지 태운다 — 안 그러면 배선은 무잠금이다.

# §8 독립 적대 리뷰 반영 (2026-08-27 · 기준 `bfadc0db`)

★**리뷰 판정은 REVISE 였고 그것이 옳았다.** 제가 자기승인했으면 **의미가 틀린 신호**가
critical 로 나갔다. 아래는 지적과 처방이며, 전부 이 브랜치에 반영했다.

## M-1 (수용) — 도달 가능성을 만든 것은 `trigger_cap` 이 아니라 `global_cap` 이었다

리뷰가 `gate()` 를 임포트해 beat=10분·6시간으로 시뮬한 결과:

```
cache_warm      n=2 → 계수차단 41건이 **전부 global_cap** · 발화 31
threshold_relax n=1 → trigger_cap 15건뿐 · 발화 **0**   (시간당 ≤4 < 임계 5)
```

즉 제 계획서·주석이 세운 의미(*"같은 트리거가 계속 치유를 원하는데 못 하고 있다"* =
`trigger_cap`)와 **실제로 발화를 만든 신호가 달랐다.** `global_cap` 은 *"지금 아픈 서비스가
여럿"* 이라는 뜻이고, 그것을 critical 로 올리면 서사(*"반복 발화했으나 효과가 없어"*)가
**거짓말**이 된다 — 전역 예산에 막힌 트리거는 **한 번도 발화한 적이 없다.**

**처방(반영)**
- `ESCALATION_COUNT_REASONS = ("trigger_cap",)` — **기록은 둘 다, 판정은 하나.**
- `_record_blocked` 에 **`reason` 을 싣는다**(안 실으면 사후에 global/trigger 를 못 가른다).
- 그러면 도달 불가로 되돌아가므로 **창을 분리**했다: `ESCALATION_WINDOW_HOURS = 3`.
  캡·임계 상수는 **여전히 불변**이다 — 캡↑(프로덕션 타임아웃 곱)·임계↓(한 번 막혀도 승격)를
  피하면서 도달 가능성을 얻는 유일한 축이라 이것을 골랐다.
  (`threshold_relax` ≈2.5건/시 × 3시간 ≈ 7.5 ≥ 5)
- 서사를 사유에 맞게 다시 썼다(*"반복해서 한도에 막혔습니다"*).

## M-2 (수용) — `global_cap` 팔이 **무잠금**이었다

변이 `in CAP_BLOCK_REASONS` → `== "trigger_cap"` 이 락 27건 전부 초록으로 **SURVIVED**.
제 락은 상수만 단언했지 그 상수가 **판정에 쓰이는지**를 안 태웠다(메모리의
「자기 상수를 단언하는 락」과 같은 형태).
→ **세 모집단 파티션**으로 배선을 태웠다: `trigger_cap` 기록+사유 / `global_cap` 기록+발화 안 함 /
`cooldown` 기록 안 함. **같은 변이 재실행 → CAUGHT 확인.**

## M-3 (수용) — 「모든 액션이 도달 가능」은 **7종 중 5종에서 거짓**이었고 락이 공허했다

제 파생형 락은 `blocked_count=ESCALATION_THRESHOLD` 를 **손으로 먹였다.** 프로덕션에서
그 값을 만들어 줄 **생산자가 있는지**는 안 봤다.

| action_type | 실제 도달 | 왜 |
|---|---|---|
| `threshold_relax` | **◎** | 유일하게 반복 `trigger_cap` 이 성립 |
| `cache_warm` | ✗ | `g_cap == t_cap == 1` 이라 global 이 항상 먼저 |
| `stale_reanalysis` | ✗ | `trigger_key` 가 인사이트마다 고유 — 반복 없음 |
| `circuit_observe` | ✗ | beat 6회/시 < `t_cap` 10 |
| `threshold_autotune` · `feature_toggle` · `prompt_ab_adopt` | ✗ | ★**생산자 없음** — `feature_flags` 가 `_record_blocked` 를 안 부른다 |

★**`threshold_autotune` 이 라이브 heal 볼륨의 441/520 = 84.8%** 인데 이 안전망은 그 액션에
대해 **여전히 발화하지 않는다.** 이건 이 PR 이 §0 에서 인용한 그 교훈(**생산 0**)의
**동일 형태 재발**이고, 규율 §D-16(*"PR 이 선언한 원칙을 그 PR 의 신규 코드에 스스로 적용했는가"*)에 걸린다.

**처방(반영)** — 주장을 **사실에 맞게 좁혔다.**
- 도달 표를 상수로 두고 **모집단 전수를 덮는지** 락으로 강제(새 액션이 생기면 판정을 강제).
- *"cache_warm 은 trigger_cap 이 원리적으로 안 나온다"* 를 **성질로** 태웠다(말로 두지 않았다).
- **생산자 부재를 락으로** 만들었다(`feature_flags` 에 `_record_blocked` 가 없음을 단언).
- L1 3종 부채를 **`strict xfail` 로 초록 안에 보이게** 남겼다 — 해소되면 빨개져 알려 준다.

★**이 PR 이 실제로 되살린 것은 `threshold_relax` 하나다.** 다만 그것이 **가장 중요한 하나**다
— 프로덕션 HTTP 타임아웃을 곱하는 유일한 이펙터라, 자동치유가 그것을 반복해서 못 하고
있으면 사람이 반드시 봐야 한다. 원결함(*"부작용 없는 `circuit_observe` 만 가능"*)과 비교하면
**의미 있는 이동**이다. 「전부 고쳤다」고 쓰지 않는다.

## M-4 (수용) — 억제가 `open` 만 봐서 `acknowledged` 하면 즉시 되살아났다

관리자 전이는 두 가지다(`routers/growth.py`). `acknowledged`(*"보고 조치 중"*) 순간
억제가 안 걸려 **다음 beat(≤10분)에 같은 critical 이 새로 생긴다** → 이 타입에서
`acknowledged` 가 **쓸 수 없는 상태**가 되고 설계가 가르려던 두 상태가 붕괴한다.

제 락은 `assert "status = 'open'" in src` 였다 — *"dismissed 를 옳게 제외"* 와
*"acknowledged 를 잘못 제외"* 를 **원리적으로 구별할 수 없었다**(한쪽만 거는 단언).

**처방(반영)** `_SUPPRESSING_STATUSES = ("open", "acknowledged")` + **파티션형 락**
(open/acknowledged 억제 · dismissed/acted 재발화) + 라우터 전이와의 **정합 락**.

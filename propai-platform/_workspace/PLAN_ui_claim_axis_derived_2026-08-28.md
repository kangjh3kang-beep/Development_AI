## 2. 변경 내용과 **회귀가 아닌 근거**

1. **문구 9개**(3키 × 3로케일): `32`→**28**, `38`→**28**. 수치를 지우지 않고 **사실로** 바꿨다.
   - 회귀 아님: 라이브가 실제로 28종만 `charges` 로 낸다(위 전제표). 32/38 은 **재분류 전 값**이다.
   - `4단계` 는 유지 — **파생 가능**해졌다(코드군 A·B·C·D = 4).
2. **락의 수집을 손 목록 → 구조 축 파생**으로.
   - `CLAIM_KEYS`(2개 하드코딩) → `CLAIM_SECTIONS`(축 선언) + `_claim_keys()`(파생).
   - 회귀 아님: 종전 2키가 파생 결과에 **포함**되는지 단언한다(축이 좁아지면 실패).
3. `_derived_counts()` 에 `stage_groups` 추가 — **순수 함수 `_stage_groups()` 로 분리**.

## 3. ★검증하지 못한 것

1. **`4` 가 허용값이 되면서 락이 아주 조금 느슨해진다.** 이 락의 설계상 「모든 정수가 파생값 중
   하나」만 보므로, 앞으로 문구에 무관한 `4` 가 들어와도 통과한다. 종전에도 `15`·`28` 에 대해
   같은 성질이었다(이 PR 이 새로 만든 결함은 아니지만, **넓힌 것은 사실**이다).
2. **축 밖의 주장 문구는 여전히 감시 밖이다.** `deepIntegration.*.subtitle` 와
   `modulePlaceholders.*.description` 두 축만 본다. 다른 자리에 역량 주장이 생기면 안 잡힌다.
   전체 파일 스캔은 날짜·가격 위양성이 폭증해 **의도적으로** 축을 좁혔다(위양성률은 측정함).
3. **`tax_regional.py` 독스트링의 `229`** 는 이번에도 손대지 않았다(사용자 표면 아님).
   그 모델이 정의하는 `regions` 테이블 부재는 **별건 부채**로 남는다.
4. **라이브 화면 확증은 배포 후에만 가능하다.** 현재는 로컬 락 + 라이브 API 로만 확증했다.
   배포 후 `projects/[id]/feasibility` 문구를 눈으로 읽어야 종결이다.
5. `en` 문구를 `38-type tax` → `28-code tax/charge` 로 바꾸며 **표현도 함께** 손봤다
   (`type`→`code`). 의미 교정이지만 **원어민 검수는 받지 않았다.**

## 4. 되돌리기 경로

- 문구만 되돌리려면: 9줄 역치환 → **락이 즉시 빨개진다**(그게 정상 동작이다).

## 2. 변경 내용과 회귀가 아닌 근거

- 백엔드 `POST /projects` 가 `Idempotency-Key` 헤더를 읽어 표준 통로(`app.core.idempotency`)로
  lookup/replay/conflict/save 한다. **키가 없으면 종전과 완전히 동일**(`if key:` 조건부 배선).
- 지문은 `create_request_fingerprint()` **순수 함수**로 분리 — 핸들러 안 한 줄로 두면 아무도 못 태운다.
- 프론트 3경로(최초 생성 2 + 고아 재전송 1)가 `projectCreateHeaders(localId)` 로 같은 키를 보낸다.

**회귀가 아닌 근거**: 헤더가 없던 종전 요청은 경로가 바뀌지 않는다. `ensure_schema` 실패는
fail-open(기억 못 함 = 일반 실행)이라 DB 장애가 생성을 막지 않는다.

## 3. ★검증하지 못한 것

- **라이브에서 재전송이 실제로 재생되는지 미측정.** 프로덕션에 프로젝트를 만들어야 재현되는데,
  그건 관측 대상(사용자 데이터)을 내가 바꾸는 것이라 하지 않았다. → 배포 후 사용자 흐름에서 확인.
- **다른 기기**의 동시 생성은 여전히 닫히지 않는다(로컬 id 가 다르다). 정직 표기이며 별건이다.
- 중복 2쌍이 이 결함으로 생겼는지는 **미측정**이고, 재구성해 보면 `#815`·`#822` 어느 쪽으로도
  설명되지 않는다. **기전 미상**으로 남긴다 — 이 변경은 *알려진 세 경로를 닫는 것*이지
  *그 2쌍의 원인을 고쳤다는 주장이 아니다*.
- `ruff` 를 **로컬 0.15.7** 로만 돌렸다(CI 는 핀 없이 최신 설치 — §32 의 버전 불일치 함정).
  import 순서는 케이스 무시 정렬 기준으로 수동 확인했으나 **최신 ruff 실행은 못 했다**.

## 4. 되돌리기 경로

단일 커밋 revert. 백엔드는 `if key:` 조건부라 프론트만 되돌려도(헤더 미전송) 즉시 종전 동작이 된다.

## 5. 잠금

| 축 | 검사 |
|---|---|
| **판단(지문)** | 이름·면적이 갈리는 두 본문이 **같은 지문** · 주소가 다르면 **다른 지문**(양성 대조군) |
| **판단(키)** | 같은 로컬 id = 같은 키 · **다른 시도 = 다른 키**(내용 키였다면 깨진다) |
| **배선(서버)** | lookup·REPLAY·CONFLICT·save·`to_response()` 다섯 지점 + **지문이 순수 함수를 경유** |
| **순서** | `save` 가 `db.refresh` **뒤**에 있다(실패는 저장하지 않는다) |
| **무회귀** | `if key:` 조건부 배선 존재 |
| **배선(프론트)** | 세 POST 경로 전수 + 고아 재전송이 **`o.id`** 를 쓴다(다른 값이면 중복) |
| **전제 P1** | `app/core/idempotency.py` 가 *"alembic 신규 헤드 없음"* 이라고 적고 있음을 테스트가 확인 — 다음 사람이 같은 오판으로 불필요한 마이그레이션을 만들지 않게 |

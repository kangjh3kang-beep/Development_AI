# 개발·CI 전용 도구 — **런타임 의존성이 아니다**(requirements.txt 와 분리).
#
# ★왜 핀하는가 (2026-08-16 실사고):
#   CI 가 `pip install ruff` 로 **버전 없이** 설치해, 실행할 때마다 최신을 받았다.
#   그날 로컬 `ruff 0.15.7` 은 All checks passed 인데 CI `0.16.3` 은 **I001 로 실패**했다.
#   **명령은 같았다**(`python -m ruff check .`). 다른 것은 오직 버전이었다.
#
#   이 형태의 위험은 크다 — ruff 가 규칙을 하나 추가하면 **코드 변경 0으로 전 PR 이 빨개진다.**
#   그리고 원인이 자기 diff 에 없어서 진단이 오래 걸린다(CI 한 사이클 ≈ 16분씩 태운다).
#
#   ★CLAUDE.md 의 "게이트는 CI 와 같은 명령으로"는 이 반쪽을 못 덮는다 — 명령을 맞춰도 뚫린다.
#     규율은 **"같은 명령 + 같은 버전"** 이어야 한다.
#
# 로컬에서 CI 와 같은 결과를 보려면:
#   pip install -r propai-platform/apps/api/requirements-dev.txt
#   cd propai-platform/apps/api && python -m ruff check .
#
# 업그레이드는 **의도된 PR** 로만 한다(그 PR 이 새 규칙 위반을 함께 해소한다).
#
# ★값은 전부 **실측**이다(임의로 고르지 않았다):
#   ruff      = 2026-08-16 CI 로그가 설치하던 버전(`Successfully installed ruff-0.16.3`) = 지금 초록인 값
#   bandit    = 같은 날 Security Scan 로그(`Successfully installed … bandit-1.9.4 …`)
#   pip-audit = 무핀 설치가 현재 받는 값(PyPI 최신 2.10.1). 로그에 설치줄이 안 남아 PyPI 로 확인했다.
#
# ★핀은 Security Scan 의 **현재 실패를 고치지 않는다**(그건 별건이다):
#   · bandit  잡 = 검사 결과로 exit 1
#   · pip-audit 잡 = `-r requirements.txt` 가 의존성을 해석하며 gdal 빌드를 시도 → `gdal-config` 부재로 실패
#     (그 단계 주석은 "설치 없이 매니페스트만 스캔"이라 적혀 있으나 **실제 동작과 다르다**)
#   최근 100회 실행에 성공이 0건이다 — 소유 세션이 별도로 봐야 한다. 핀은 그 진단을
#   **재현 가능하게** 만들 뿐이다(버전이 매번 달라지면 원인 분리가 안 된다).
ruff==0.16.3
bandit==1.9.4
pip-audit==2.10.1
